# Two-cluster job delegation (opt-in)

Run from the repository root with an activated `.venv`:

```sh
env -u PYTHONPATH make test auth-keycloak-gmolto cluster-localhost cluster-run \
  ROBOT_SUITE=tests/federation/job-delegation.robot
```

The **first** `cluster-*` selects the origin and the **second** selects the destination. Both are resolved from `variables/.env-cluster-*.yaml`; the auth file supplies one Keycloak identity authorized on **both** clusters. These are test configuration names, not `oscar-cli` profile names. For example, `cluster-run` may correspond to the CLI profile `run.oscar.grycap.net-grycap`, but the test does not hard-code either name or use the CLI. The two endpoints must differ. When clusters need different host-side and inter-cluster addresses, set optional `OSCAR_FEDERATION_ENDPOINT` in **each** cluster variable file; Robot still calls `OSCAR_ENDPOINT` from the test host, but the rendered FDL uses the federation address for server-to-server requests. Without that option, the FDL uses `OSCAR_ENDPOINT` as before. Both federation URLs must be mutually reachable from the clusters, and the ingress routes must accept their hostnames. For the two local Kind clusters, the host-side URLs are `https://localhost.direct` and `https://localhost.direct:444`, while the federation URLs are `https://oscar-test-zwj-control-plane:30443` and `https://oscar-test-yzg-control-plane:30443` respectively; these require local HTTPRoutes that accept the node names and `SSL_VERIFY: False` with the current local certificates.

**Quota selection:** each test reads `/system/quotas/user` on both clusters and chooses a request that occupies about three quarters of the origin's free CPU (or free memory if CPU does not fit on the destination). The service's own Knative instance then deploys on the origin with headroom — the fixture waits for its deployment to become ready — while a second reservation of the same size (the Job) cannot be admitted next to it, which is what makes OSCAR delegate. The request also fits two simultaneous reservations on the destination (the propagated worker service and its Job). `DELEGATION_CPU` and `DELEGATION_MEMORY` are minimum requests, not fixed values; `DELEGATION_IMAGE` is configurable with `ROBOT_ARGS="-v DELEGATION_IMAGE:ubuntu:22.04"`. The API-invocation case checks quotas again immediately before its POST; the upload-trigger case checks just before its PUT; both wait until the origin's live free quota reflects the deployed service's reservation. Neither changes cluster quotas or creates a filler workload. If either origin maximum is zero (OSCAR treats it as unrestricted), or no request fits on the destination, the fixture fails before deployment. Concurrent quota changes, destination physical capacity, and Kueue admission can still prevent execution. Both clusters must accept the same OIDC identity; the image must be permitted on both. Do not point this test at production without approving the service/job side effects.

The Robot suite renders an FDL based on OSCAR-Hub's `crates/simple-test/fdl.yml` and its sibling `script.sh` **in memory**. It keeps the Hub image, MinIO input/output and text-analysis behavior, with unique bucket/service names, a per-run log marker, dynamic resources and federation settings. For two local Kind clusters, the optional `OSCAR_FEDERATION_MINIO_ENDPOINT` in the origin's variable file routes the worker's MinIO traffic to the origin's NodePort; it contains no storage credentials. The suite injects the OIDC refresh token into the API request without writing a populated FDL, and deploys the federated origin service through OSCAR's API (which propagates a worker service). It uploads unique text to a `fixtures/` object outside the configured `input/` notification prefix (so the upload cannot trigger an extra job), then POSTs a MinIO-format event referencing it. The event's `storage_provider` is the provider **ID** `default`, not the FDL name `minio.default`; using the latter can process the event payload as the input instead of downloading the object. It requires a successful destination Job with the unique marker in its logs, no Job on the origin, and verifies the produced `output/` object on the origin contains the original text and the expected word/character counts. In the API-invocation case, OSCAR's presign API supplies short-lived URLs for the fixture upload and read-back; the signed `Host` is preserved when connecting through the local NodePort. The host-side MinIO address defaults to `http://localhost:<port from OSCAR_FEDERATION_MINIO_ENDPOINT>` for local endpoints; for other networking setups, supply `ROBOT_ARGS="-v MINIO_TEST_ENDPOINT:<host-accessible-Minio-URL>"`. By default it cancels all Jobs belonging to each newly created test service (including suspended or still-running Jobs), deletes the origin and worker services even if a test fails, then reads back service absence; **service deletion may also remove the buckets managed by those services**. It does not delete unrelated or pre-existing services, and `KEEP_SERVICES:True` skips all teardown deletions. It never changes quotas or deletes unrelated jobs. Without a second cluster, this suite skips itself under `ROBOT_SUITE=all`; other suites are unaffected.

The second test uses a separate, uniquely named service/bucket pair. It retrieves the authenticated OIDC user's MinIO credentials from `/system/config` in memory, then uploads once to that service's `input/` prefix with S3 (`boto3`). Unlike OSCAR's administrator-signed presign URL, this makes the MinIO notification identify the service owner, so OSCAR checks the correct user's quota before deciding to delegate. It does **not** call `/job`; it requires exactly one Job on the destination, none on the origin, and the expected output in the origin bucket. The post-upload read-back still uses a presigned GET, which cannot trigger an extra Job. This tests the MinIO notification/webhook path independently of the API-invocation case. Each test has its own fixture and teardown. Do not increase Robot's logging to reveal the `/system/config` response or S3 credentials.

To keep the created services, their buckets and terminal Jobs for inspection, use the explicit opt-in flag (the console prints each test's generated names):

```sh
env -u PYTHONPATH make test auth-keycloak-gmolto cluster-localhost cluster-localhost-replica \
  ROBOT_SUITE=tests/federation/job-delegation.robot ROBOT_ARGS="-v KEEP_SERVICES:True"
```

`KEEP_SERVICES:True` skips **all test teardown deletes**, including on a failed test after fixture creation. Clean up these test-owned resources manually when no longer needed; running the suite again creates new names and does not reclaim the previous ones.

For a syntax-only check without any cluster requests:

```sh
env -u PYTHONPATH make test auth-keycloak-gmolto cluster-localhost cluster-run \
  ROBOT_SUITE=tests/federation/job-delegation.robot ROBOT_ARGS=--dryrun
```
